The Shop That Ships Itself

Three items, one storefront, zero manual work. Stripe collects the money and the address, Printful prints and ships, and nobody confirms anything by hand — plus the one rule that keeps it from ever losing money.

By Propagation House September 23, 2026

The question that started this was a simple one and it turned out to be the whole project: why are we still absorbing shipping costs? We had a shop with three products, a storefront that looked finished, and a checkout that was, on paper, automated. But paper is where the automation stopped. Somewhere between the buy button and the shipping label, the money was quietly coming out of our pocket.

Three items, zero manual work

The shop is small on purpose — a hoodie, a tee, and a beanie. Three SKUs, three product pages, one config file. The whole thing is designed to be boring and reliable, because a storefront you have to babysit is a storefront you stop wanting to run.

The pipeline that runs it is the interesting part. When a buyer picks a size and hits Buy — $55, the shop posts to a serverless function that mints a Stripe Checkout Session on the fly. Stripe collects the payment and the shipping address. Then it redirects back to a thank-you page, which calls a second function that verifies the payment is actually paid, pulls the address Stripe collected, maps the product and size to the right Printful variant, and creates a confirmed order. Printful prints it and ships it.

Nobody touches any of it. No manual payment links, no hand-confirming orders, no copy-pasting a shipping address from an email. The chain is: Stripe → Printful → production → shipping. Hands-off.

“The chain is Stripe to Printful to production to shipping. Hands-off.”

The one rule that keeps it honest

Shipping was the first thing we found. The checkout was sending no shipping options at all, and the Stripe account had zero shipping rates — so buyers paid nothing for shipping and we absorbed it inside the margin. That is survivable for a while and then it is not.

The fix was a decision, not a calculation: charge every buyer the highest rate Printful would apply, which is the Canada rate (hoodie $10.59, beanie $7.29). American buyers overpay by a couple of dollars — a tiny subsidy we accepted for simplicity — and Canadian buyers are covered exactly. The result is a guarantee: no order ever loses money, no matter where it ships. We ran every destination through a cost model and the worst case was still comfortably positive.

That is the rule the whole shop rests on. And it is enforced in more than one place, because the first thing this project taught us is that a guard in the browser is not a guard.

The bugs that would have cost us

Building this, we kept finding the same class of mistake: the client looked right, and the server was wide open. The tee is the cleanest example. It costs $41.96 to fulfill against a $30 price — a negative $11.96 on every single sale. The buy button was hidden, so it looked fine. But a direct POST to the checkout function would still mint a live Stripe session for it. The fix was a server-side sold-out guard that refuses the product before a session is ever created. Sold out is not a style choice; it is a server rule.

Two more of the same species. The order-creation function was posting to Printful without a store_id — Printful silently returns a 400 and the order is never created, so a buyer could pay and get nothing. And the thank-you page runs on every page load, so without idempotency a single refresh could double-order. Both fixed by making the server the source of truth: the store id is required, and the order id is written back onto the Stripe session so a replay returns the original order instead of creating a second one.

There is also a quiet one that only shows up in production: Vercel auto-parses JSON request bodies, so calling JSON.parse on an already-parsed object throws. That one had been silently breaking the buy button for a while, and it only surfaced when we tested the actual request path rather than just the Stripe key.

What it taught us

The lesson underneath all of it is the same one, and it is worth writing down: the server is the guard. A button can be hidden, a price can be edited, a URL can be hit directly — none of that is enforcement. Every rule that matters — sold out, price, shipping, idempotency — has to live in the code that runs when the request arrives, not in the markup that renders the page.

The second lesson is about verification. We found the shipping gap because we asked whether the checkout was actually good, and we found the store-id bug because we tested the outbound URL instead of trusting that the handler ran. A test that only counts calls proves the handler ran; it does not prove it called the right endpoint with the right parameters.

And the third is the one we keep coming back to. A storefront you have to babysit is a storefront you stop wanting to run. The goal was never just to sell a hoodie — it was to make the selling disappear into the background, the way a good tool does. Three items, one config file, and a chain that runs itself. That is the whole point.
